# Protect South Portland static site — agent notes

Static HTML/CSS site for Protect South Portland, generated into `docs/` by `tools/build.py`. GitHub Actions on this repo only runs the test suite, a build smoke check, and the non-blocking scheduled staging audit (issues only — nothing in this repo's CI deploys). The public site lives on the Pages mirrors (`cristoslc/protect-south-portland-published`, plus the staging rehearsal `cristoslc/protect-south-portland-staging`) and is updated only through `tools/publish.py` under the staging-first deployment policy below.

## Deployment policy — staging first, prod by exception (operator directive, 2026-10-14)

Every change reaches the public site through the staging mirror first; production is only a reviewed second step. The ladder, always in this order: gate report → staging publish → staging review → prod publish. Every publish also runs the changelog handoff at rung 2b: the changelog lieutenant gets the commit, the changed pages and the gate report before the staging leg, drafts the entry there, and captures the changed pages on staging once that build is live, before any prod leg. The changelog is a reader-facing digest; the ledger remains the system of record, and a capture is never proof of staging secrecy. The staging leg is the publish tool's bare default — `python3 tools/publish.py --gate-report ../gate-reports/<date>.json` targets `cristoslc/protect-south-portland-staging` (hardened 2026-10-14 so a bare run cannot reach production) and keeps the staging custom domain automatically; its URL is `https://staging.protectsouthportland.org`. Production is reachable only with the explicit flag `--repo cristoslc/protect-south-portland-published`, and nothing goes to prod until the staging leg has an explicit operator sign-off in the thread on top of green automated checks.

A prod push that skips staging (prod-direct) is reserved for extreme exceptional circumstances: it requires the operator's explicit in-thread authorization before it runs, and it must be recorded with a `--note` naming the exception on the publish commit plus a ledger row. The release gate (below) is never skipped by any leg. The full step-by-step runbook lives at `../docs/runbooks/psp-staging-first-deployment.md` (workspace-root `docs/runbooks/`, sibling of this repo). The staging leg also applies the row-42 obscurity gate (staging target only, never on prod): a Disallow-all `robots.txt`, a per-page `noindex, nofollow` meta, and a JS cookie gate keyed to `PSP_STAGING_PASSPHRASE` (env or the workspace-root `.env`; only its SHA-256 embeds; a missing value refuses the leg loud); the `staging-gate` marker is a private-surface marker, so a gated tree can never reach production quietly. The gate is deterrence-grade by design (Pages serves full HTML; see ledger row 42). At that same boundary the leg also writes the row-79 publish-time line into every staged page's masthead: a small `Staging preview, updated <date and time>` strip above the logo and nav row, whose time comes from the publish clock in South Portland's timezone (`America/New_York`) and is never typed into a page, with its `staging-updated` marker in the same private-surface set so a stamped tree fails a prod leg's scan by name. Neither row is ever applied by a production-targeted leg. Both injections are wrapped in paired marker comments, and `tools/publish.py`'s `strip_injected_blocks` (or the `served_page_matches` comparison built on it) removes every injected region in one place, so a page fetched from staging hashes back to the gate report's `sha256`. Any served-vs-report or served-vs-build comparison must run that strip first: a raw byte diff of a staging page always differs from the build by exactly those two blocks, and a comparison that fails for that reason invites a waiver instead of catching a real change.

Before any staging or production leg, invoke the `psp-changelog` skill at `.agents/skills/psp-changelog/SKILL.md`. The `--changelog-handoff` flag is a hard requirement of `tools/publish.py`, not an optional courtesy.

## Staging audit — non-blocking, automated (2026-10-15)

`tools/staging_audit.py` audits the staging mirror on a schedule and files one digest issue per run on this repo, labeled `staging-audit` + `accessibility` (create-if-absent). Schedule: weekday mornings ~13:15 UTC plus manual `workflow_dispatch`, via `.github/workflows/staging-audit.yml`. Per run it checks every public page for HTTP 200, runs Lighthouse accessibility (desktop) on all pages plus a mobile pass on `index.html`, re-checks the typography floor against the `styles.css` staging actually serves (root `112.5%` + body `1rem` — the same contract `test_typography_older_visitor_floor` pins on the source file), and diffs its findings against the previous run's digest, read from the machine JSON block inside the last `staging-audit` issue.

The UAT cycle's visual sweep is `tools/uat_snapshots.py` (per-page full snapshots at the five evidence widths into `tests/evidence/uat-snapshots/`; gate-aware via the shared passphrase; manifest.json is the capture-of-record) and the judge's reading protocol — the layout hermeneutic — lives at `../docs/runbooks/psp-visual-uat.md`.

**Non-blocking contract:** a site-shaped problem (404, Lighthouse failure, floor miss) records a finding and still exits 0 — the audit must never block a deploy pipeline through its own exit code. It exits 1 only when the environment is broken (staging unreachable, Lighthouse crash, gh failure), and those failures are loud. Local ad-hoc pass: `python3 tools/staging_audit.py --base-url <url> --skip-issue` (stdlib only; Lighthouse arrives via npx). Since row 42 the audit passes through the staging cookie gate: it reads the passphrase like publish does and attaches the byte-compatible `psp_staging` cookie to every fetch and Lighthouse run (missing passphrase is loud only when the target is the default staging URL). The a11y contract this audit guards lives in `../psp/brand-guides/WCAG_COMPLIANCE.md` (verified contrast-pair table, typography floor, known deviations).

One operational fact from the first run day (2026-10-15): an audit racing a Pages rebuild can read a stale serve (the digest's typography findings then flag the OLD stylesheet). The deltas self-heal — the next run records the stale findings as resolved — so a run right after a publish should be read together with whatever follows it.

## Public website release gate (operator directive, 2026-10-13 — applies before ANY publish or republish)

1. **Scope:** every page whose copy changed (on the first run: all pages). A page is not publishable until it passes a full humanizer + style review.
2. **Reviewer:** the review round runs on a GLM-5.3-class model or higher, and flash variants do NOT qualify (operator clarification 2026-10-13): use `ollama-cloud/glm-5.3` (full GLM-5.3) or anything above it in the model ladder. A model below that class may implement revisions, but never performs the review verdict. Verbatim material copied from the historic Wix site is NOT exempt — it is legacy campaign copy and needs the review most.
3. **Rounds:** revise and re-review up to 3 rounds against the humanizer + style findings. Any page that still fails after 3 rounds is NOT published — escalate to the operator for a rewrite instead.
4. **Draft-artifact scan (part of every review):** no internal-draft language may reach the public surface. Known example (found live on `past-work.html` 2026-10-13): the header `THE #1 GOAL AS NOW WRITTEN IN THE MOST RECENT DRAFT:` — a working-draft label that must never be published. Scan for that pattern class: "as now written", "most recent draft", TODO/FIXME labels, template placeholders, anything that reads like a note to self rather than public copy.
5. **Recording the pass:** note per-page review outcome (round count, pass/fail) in the change log/commit message when publishing through the mirror pipeline.
6. **Content-addressed report, full-class reviewer (2026-11-04):** each page entry carries the `sha256` of the built `docs/<page>.html` as reviewed, and the report states `"review_class": "full"`. The publisher refuses a page whose current file hash differs from the reviewed one, refuses an entry with no hash (legacy reports do not publish; a missing hash cannot prove what was reviewed), and refuses a missing class or a `review_model` carrying a flash marker. A verdict therefore travels with the content it reviewed: an unchanged page legitimately keeps an older verdict, an edited page is refused by name. Write reports with `tools/gate_report.py`, which stamps the hashes and validates the class.

## Publishing to the public mirror

Publishing is one command: `python3 tools/publish.py --gate-report <path.json>`. The gate report carries the reviewer's per-page outcomes (`{"date", "review_model", "review_class", "pages": {"<page>.html": {"rounds": N, "outcome": "pass", "sha256": "<hash of built docs/<page>.html>"}}}`); every page in `site/pages/` must be present and passing, with a hash matching the file as it stands now and a full-class reviewer, or nothing is pushed. Since the 2026-10-14 hardening the tool's default target is the staging mirror, so the flag-less command is the staging leg, and production is reachable only with an explicit `--repo`. Two flags still retarget the pipeline: `--repo <owner/name>` swaps the push target and Pages verification URLs (e.g. `cristoslc/protect-south-portland-published` names production, `cristoslc/protect-south-portland-staging` staging), and `--domain <hostname>` stages that hostname as the tree's `CNAME` and sets it as the target repo's Pages custom domain. Without `--domain` a publish auto-keeps the custom domain its target already carries (re-staged and re-verified, never silently dropped), which is why the staging leg needs no domain flag. For a `--domain` publish the tool then verifies `https://<hostname>` end to end: waits up to 8 minutes for the domain to serve, requires a hostname-valid TLS certificate (SNI + SAN matched), requires 200s, and requires the served index to match the freshly built `docs/index.html` once the row-42 gate block and the row-79 staging stamp are stripped, and the comparison is strict: a served index that differs after the strip stops the leg, with no banner-line fallback; then it polls the Pages API for `https_certificate` approval and sets `https_enforced=true` (`--no-wait-https` skips that wait and leaves enforcement manual; `--wait-https` forces the wait; both flags are invalid without `--domain`). On the enforcement timeout it fails loud with the manual step: repo Pages settings → Enforce HTTPS.

What it does, in order, failing loud at every step: runs the test suite → builds `docs/` (including copying the standalone map pages into `docs/map/` from the tank-farms checkout, or `PSP_MAP_DOCS_DIR`) → stages the publish tree (`docs/` minus `CNAME`/`.gitkeep`, plus a fixed README and `.nojekyll`) → scans the whole staged tree for private-surface markers (research links/labels, the private repo name and its github.io host, wixstatic, the Oct 15 assembly, draft artifacts, internal file names — the sets live in `tools/psp_public.py`) → force-pushing a single fresh commit ("Publish <date>", orphan history replaced every time; a same-day republish keeps the original subject and records its incremental note in the body, via `--subject`/`--note`) to `cristoslc/protect-south-portland-published` → enables Pages from `main` root and waits for the URLs to serve. The wait refuses to follow redirects outside the allowed hosts: the github.io check requires the final URL to stay under `*.github.io`, so a redirect elsewhere (the custom domain already live, or NetSol forwarding to Wix) aborts with "custom DNS already live — verify the custom domain instead, or DNS not yet moved" instead of passing over the wrong site's bytes or timing out confusingly late. A publish can never silently wipe a target's Pages custom domain: without `--domain` the existing hostname is auto-kept, `--allow-domain-drop` is the only way a staged tree drops one, and a verified domain whose cname cannot be read refuses a domainless run before anything is built or pushed. It always prints the Pages settings it saw (build status, cname, certificate state, protected state, https_enforced). `--mirror-dir <scratch>` runs the same staging + scan + commit against a local git repo without touching GitHub.

Map pages: `docs/map/{embed.html, map.html, styles.css}` are generated from the tank-farms repo (embed verbatim — it is chrome-free by construction; map.html is stripped of the research nav + sidebar links). build.py never deletes an existing `docs/map/`, so a CI checkout with the committed copy keeps serving the relative `map/embed.html` iframes with or without the sibling repo present.

The `CNAME` stays in the site repo, staged for the domain flip; when the operator flips DNS to the mirror, publish with `--domain protectsouthportland.org` (stages the `CNAME` and sets the mirror's Pages custom domain — `PUBLISH_EXCLUDES` only keeps an unstaged `CNAME` out of the tree). Any other hostname works the same way through `--domain` on any `--repo` target, e.g. the staging mirror's `staging.protectsouthportland.org` (row 41, 2026-10-15: renamed from the opaque `staging-b1fa9840` label — the operator's NetSol zone rows already answer the new name).

## Editing flow

Edit `site/pages/*.html` (each file carries its title/description in the first-line `<!-- meta: ... -->` comment), run `python3 tools/build.py`, run the tests, commit, push to `origin/main` (CI runs the tests and a build smoke check only — it deploys nothing), then follow the deployment policy above before anything reaches a public mirror. After any layout/nav change, run the multi-viewport pass (`tools/visual_check.sh`) before reporting — 412/768/1440 screenshots of homepage + campaign page (top band + footer region); the harness defaults to a local http server over fresh `docs/` (explicit baseUrl overrides), waits for network idle, and runs validity guards (200 preflight, differential checksums, non-uniform crops), so a blank capture can never exit 0. Old merged pages (`oil-tank-emissions.html`, `vocs.html`) live on as redirect stubs written by `tools/build.py` REDIRECTS.
